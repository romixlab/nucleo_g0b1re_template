A complete, working starting point for a [WireWeaver](https://github.com/vhrdtech/wire_weaver) device on the
[ST Nucleo-G0B1RE](https://www.st.com/en/evaluation-tools/nucleo-g0b1re.html) board (STM32G0B1RE, Cortex-M0+):
firmware, a typed API, a Rust client library, a command line and a Python module, all from one API definition.
Use it as a GitHub template ("Use this template"), rename it, add your own methods, properties and streams.

The firmware was generated by the [embedded_bedrock](https://github.com/romixlab/embedded_bedrock) firmware
template and talks to the PC through the board's own ST-LINK (RTT), so nothing but the Nucleo and its USB cable
is needed. The same layout fits a board with a USB connector by switching the transport (`bedrock_fw.json` records
the generator answers; see AGENTS.md).

| directory | |
|---|---|
| `nucleo_g0b1re_api/` | `#![no_std]` API crate: the `NucleoG0b1reApi` trait and its data types, shared by the firmware and every host |
| `firmware/` | the firmware (embassy, defmt): `src/ww.rs` and `src/ww/device.rs` implement the API, `src/settings.rs` the settings store, `src/last_reset.rs` the crash record, `src/log.rs` the stored log, `src/boot.rs` the reboots into the ROM bootloader |
| `nucleo_g0b1re_client/` | Rust client library: typed methods over the generated WireWeaver client |
| `nucleo_g0b1re_cli/` | `g0b1re`, the command line over the library |
| `nucleo_g0b1re_py/` | `nucleo_g0b1re`, the Python module over the library (PyO3, maturin) |
| `scripts/rename.py` | gives the project your own name, `just rename` |

What the firmware has from the start: a WireWeaver API over RTT with the device contract under `device` (firmware
name, version, commit, build id; board, unique id and chip; last reset cause with the crash record of a HardFault or
panic; a label and settings stored in flash; the `cnt` event counters in RAM and in backup registers; the defmt log,
kept in RAM across a reset; reboots into the STM32 ROM bootloader and a boot-loop rescue), a settings store in the
last 8 KiB of flash with ECC-safe reads, flip-link stack overflow protection, the ES0548 dual-bank prefetch guard. [FEATURES.md](FEATURES.md) lists all of it
with its status; [CHANGELOG.md](CHANGELOG.md) the changes.

## The board

![Nucleo-G0B1RE top view: every header pin, coloured by what it is for](docs/board/nucleo_g0b1re-top.svg)

Green pins are free, orange ones have a job on the board by default that a solder bridge removes (PA2/PA3 go to
the ST-LINK's virtual COM port, PA5 drives LD4, PC13 is the USER button, PF0 carries the ST-LINK's 8 MHz MCO), red
ones are the debug port and reset. [docs/board/](docs/board/) has the bottom view with every solder bridge and its
default, the power tree (USB, VIN, E5V, the JP2 selection, the regulators) and
[the pin table](docs/board/nucleo_g0b1re-pins.md) with a note per pin; `just board` re-draws them from
`docs/board/nucleo_g0b1re.toml` with [boardmap](https://github.com/romixlab/embedded_bedrock) (bedrock_board).

**B1, the user button:** PC13, pulled up to VDD through R29 (reads `1`) and pulled to GND when B1 is pressed
(reads `0`); SB20 (ON by default) ties B1 to PC13, OFF frees the pin (UM2324 §6.11; R29/SB20 nets from the
MB1360-G0B1RE-C02 schematic).

**LD4, the user LED:** PA5 drives it through a MOSFET (T2), high lights it, SB22 (ON by default) wires PA5 to
it (UM2324 §6.10 point 4). PA5 is also `TIM2_CH1_ETR` (alternate function 2, STM32G0B1xx datasheet DS13560): a
PWM there can breathe the LED instead of a plain on/off GPIO. **LD1 (COM)** is driven by the ST-LINK/V2-1
itself, not the target MCU, and blinks red/green to show USB enumeration and PC↔ST-LINK↔STM32 communication
state; **LD3 (PWR)** is on whenever the board's 5 V rail is present (UM2324 §6.10 points 1 and 3).

**CN4, the SWD target jumpers:** both ON (default) route the ST-LINK/V2-1's SWD to the on-board STM32G0B1RE;
both OFF route it out to CN11 instead, to program or debug an external target board (UM2324 §6.4.3, §6.4.4,
Table 6). Don't wire CN11 while CN4 is ON, it can disturb the on-board link.

## Setup

With [just](https://just.systems/man/en/packages.html) and [uv](https://docs.astral.sh/uv/getting-started/installation/)
installed (Windows: `winget install Casey.Just` and
`winget install astral-sh.uv`):

```sh
just setup               # rustup, the thumbv6m-none-eabi target, probe-rs, flip-link, cnt, ww, boardmap, git hooks
just setup --check       # only report what is missing
```

`scripts/setup.py` runs on Arch, Ubuntu / Debian and Windows and skips what is already there. Before it changes
anything it prints its plan. Some steps fetch a script from the internet and run it, the way these tools are meant
to be installed: rustup's installer (`https://sh.rustup.rs`; on Windows winget installs rustup), probe-rs's installer
(on Windows its PowerShell installer, run with `irm | iex` and `-ExecutionPolicy Bypass`), and probe-rs's udev rules
file, pinned to a commit, written as root. The plan names each of them before it runs.

Steps that need root or an administrator are printed for you to run, never run behind your back: the system
packages (a C compiler, git, curl; on Windows the MSVC build tools), the udev rule that lets you open the ST-LINK on
Linux ([probe-rs](https://probe.rs/docs/getting-started/probe-setup/)) and ST's ST-LINK driver on Windows.
`just setup --root` runs them too, each shown first; `--no-probe` leaves out the probe's udev rule or driver (a build
server), `--skip TOOL` leaves out one step.

The last step turns on the project's git hooks (`just hooks`, see [Changing the API](#changing-the-api)): for each
hook in `.githooks/` it puts a small hook into `.git/hooks/` that first runs the hook that was there before (kept as
`<name>.chained`) and then the tracked one, so hooks you or other tools installed keep working. It does not set
`core.hooksPath`; when that is set already, it prints the line to add to the hooks there. `just hooks --remove` takes
them out again and puts the old hooks back.

## Run

```sh
just run                 # build, flash and run the dev firmware with its defmt log (Ctrl-C: the firmware keeps running)
just cnt                 # same, but through `cnt run`: defmt log plus the event counters as they change
just flash               # release firmware through the probe
just install             # build and install the `g0b1re` command line
g0b1re info              # API, firmware, build id, board, chip, label, last reset
g0b1re led blink -n 5
g0b1re label "bench 1"   # stored in the board's flash
g0b1re last-reset --clear
```

The recipes and `cargo run` use only the Nucleo's own ST-LINK/V2-1 (USB id `0483:374b`), never another probe on the
PC; with two Nucleos attached, `G0B1RE_PROBE=SERIAL` (from `probe-rs list`, in the environment or in a `.env` file)
picks one. A probe can be opened by one program at a time: stop `just run` / `just attach` before using `g0b1re`. Connecting
scans the RAM for the RTT control block (about 1.5 s through an ST-LINK); `--elf firmware/target/thumbv6m-none-eabi/debug/nucleo_g0b1re`
(or `G0B1RE_ELF`) takes the address from the firmware's ELF instead. With several probes attached, `--probe SERIAL`
(`g0b1re probes` lists them, and the shell completes the serials: `source <(COMPLETE=bash g0b1re)`).

`cnt tui --chip STM32G0B1RETx` shows the event counters; `ww` (the WireWeaver CLI,
`cargo install --git https://github.com/vhrdtech/wire_weaver wire_weaver_cli`) can introspect and call any API
without the generated client: `ww --rtt STM32G0B1RETx introspect`.

## Device

Each part of the device contract (`device` in the API, the same traits as other WireWeaver devices) has its own
`g0b1re` command. Stop `just run` first; `just flash` and `just run` put the firmware's ELF into the ELF directory
(`cnt elf add`), so `counters`, `log` and `report` find it by the build id the board reports (`--elf FILE` names one,
`--force` takes it although its build id differs).

```sh
g0b1re firmware          # name, version, git commit, build time and profile, build id
g0b1re board             # NUCLEO-G0B1RE rev C02 (Assumed), serial = the chip's unique id
g0b1re uid               # the 96-bit unique id
g0b1re variant           # STM32G0B1/G0C1 (0x467) rev A (0x1000), 512 KiB flash: DBGMCU_IDCODE and the flash size register
g0b1re label "bench 1"   # the label, in flash; `g0b1re label` shows it
g0b1re last-reset        # reset cause and boot count, the crash record after a HardFault or panic
g0b1re counters          # every cnt counter, RAM and backup registers
g0b1re counters --reset ram
g0b1re log               # the defmt log the board keeps, decoded; the board keeps it as it is
g0b1re log -f            # then every new line as it is logged, until Ctrl-C
g0b1re settings show     # led-at-boot
g0b1re settings led-at-boot on   # LD4 lights at boot (try it: press RESET, B2)
g0b1re settings reset    # every setting back to its default, the label too
g0b1re boot state        # Confirmed: the firmware is the only image
g0b1re boot reboot       # reset into the firmware
g0b1re dfu               # the update node: product, profile InPlace, boot state, last result
g0b1re report            # all of the above in one text, for a bug report
```

The log lives in RAM that a reset keeps, so after a crash `g0b1re log` still shows what led to it. When a host
reads it, the board may drop what was read already to make room: a `--- N log messages lost (Store) ---` line at the
start says so, the lines after it are complete.

**The ROM bootloader.** `g0b1re boot reboot --updater` resets the board into the STM32 ROM bootloader, and so does
the firmware itself after four boots in a row that each ended within 10 s (a boot loop: the next firmware reports
it as `last result  Recovery` in `g0b1re dfu`). The ROM bootloader's USB DFU is on PA11 / PA12 (USB D- on CN10-14, D+ on CN10-12), which
a Nucleo-64 brings only to the morpho header CN10, not to a USB connector: to use it, wire a USB cable to those pins
and GND. ST's AN2606 lists the ROM's other interfaces. The ROM bootloader stays until the next reset (B2, a power
cycle), which starts the firmware again; the probe reaches the chip whatever runs on it, so `just flash` works from
the ROM bootloader too. Flashing four times within 10 s of each other counts as a boot loop as well: the fourth boot
lands in the ROM bootloader, the next reset or flash comes back.

## Python

```sh
just py                  # builds the module into nucleo_g0b1re_py/.venv, opens a prompt with the board as `dev`
just py-example          # nucleo_g0b1re_py/examples/blink.py
just py-example device   # nucleo_g0b1re_py/examples/device.py: the device contract
just test-py
```

```python
import nucleo_g0b1re
with nucleo_g0b1re.Device() as dev:         # Device(probe_serial="...", elf="firmware/target/.../nucleo_g0b1re")
    print(dev.firmware())
    dev.label = "bench 1"
    dev.blink(count=3, period_ms=400)
    print(dev.board(), dev.variant(), dev.uid())
    print(dev.last_reset())
    print(dev.counters())                   # {"RAM/loop_iterations": 139, ...}
    print("\n".join(dev.log()))
    dev.led_at_boot = True                  # dev.reset_settings() puts the defaults back
    print(dev.boot_state(), dev.dfu_node())
    dev.reboot()                            # reboot(updater=True): into the ROM bootloader; disconnects
```

## Make it yours

1. `just rename my_board` (`just rename my_board mb` to call the command line `mb`): crates, directories, the API
   trait, the binary and its environment variables. Then read `README.md`'s prose and the `description` lines.
2. Add to the API in `nucleo_g0b1re_api/src/lib.rs`: a method, a property or a stream of the `NucleoG0b1reApi`
   trait ([WireWeaver docs](https://github.com/vhrdtech/wire_weaver/tree/master/docs)). The user button B1 (PC13) as
   a readable property is a good first one.
3. Implement it on `ServerState` in `firmware/src/ww.rs`: the compiler lists what is missing. Put the peripherals it
   needs into `ServerState` (`firmware/src/main.rs`).
4. Add a typed method to `Nucleo` in `nucleo_g0b1re_client/src/lib.rs`, a subcommand in `nucleo_g0b1re_cli/src/main.rs`
   and a method of `Device` in `nucleo_g0b1re_py/src/lib.rs`. The generated client (`board.raw()`) already has every
   item, the typed layers are for the names and errors.
5. Bump `nucleo_g0b1re_api`'s version: the crate name and version identify the API on the wire. Which bump a change
   needs is checked, see [Changing the API](#changing-the-api).

`just test` and `just lint` run what CI runs: the host workspace, the firmware (dev and release build) and the
Python module. `just deploy` brings a PC and the board on its probe up to `main` in one step.

## Changing the API

Firmware already on boards and hosts built against an older API keep working together as long as the API only
changes in compatible ways ([WireWeaver's evolution rules](https://github.com/vhrdtech/wire_weaver/blob/master/docs/evolution/rules.md)).
Every released version of `nucleo_g0b1re_api` has a snapshot of its traits and types in
`nucleo_g0b1re_api/api_snapshots/`, committed with the release, and a test of the API crate
(`nucleo_g0b1re_api/tests/evolution.rs`) compares the source with the newest snapshot. It fails when the API changed
without the version bump the change needs, and names the version to put into `nucleo_g0b1re_api/Cargo.toml`:

- a compatible change (a new method, property or stream at the end of the trait, a new type) needs the compatible
  position: `0.1.0` -> `0.1.1` before 1.0, the minor after;
- a breaking change (a method renamed or removed, a new one inserted between existing ones, a changed argument
  type) needs the breaking position: `0.1.0` -> `0.2.0` before 1.0, the major after.

The flow:

1. Change the trait in `nucleo_g0b1re_api/src/lib.rs` and bump the crate's version; `just api-check` runs the check
   on its own (`just test` and CI run it too).
2. Commit. With the hooks on (`just setup` or `just hooks`), `.githooks/pre-commit` runs `just api-check` whenever
   the commit touches `nucleo_g0b1re_api/` and refuses the commit while the check fails. `git commit --no-verify`
   skips it for a work-in-progress commit; CI still checks.
3. When the version is released (flashed to boards, a host tool shipped), record it with `just api-save`
   (`ww api save`, which refuses a version that is not bumped enough) and commit the new file in `api_snapshots/`.
   Until then the check compares with the previous release, so the version can stay bumped while you work.

A missing snapshot fails the check too, so it is never skipped by accident; `just rename` removes the template's
snapshot and saves the renamed crate's first one.

## Template upgrades

`bedrock_fw.json` records the generator version and every answer; `AGENTS.md` has the upgrade procedure an agent
follows (regenerate, compare, apply what you approve). Dependencies come from git and are pinned by the two
`Cargo.lock` files (`firmware/Cargo.lock` and the root's).
